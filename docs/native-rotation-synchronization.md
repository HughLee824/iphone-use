## 已复现的问题

本次工具链为 macOS 27.0 (26A428)、Xcode 27.0 (27A266a)，设备发现选择的有线 iPhone 12 Pro / iOS 27.0 (24A437)。全部输入发生在普通 Probe，未启动 Runner。

同一标准会话先由竖屏转左横屏，再转右横屏，前两次截图与显示方向正确。右横屏独立角落 B 从 1→2 后，再转左横屏，动作后的 PNG 与稍后独立观察的 PNG 均倒置，Apple 显示信息仍为 `rot270`。独立 CLI 查询和 `displays --stream` 订阅也没有及时更新；因此不能把重复读取相同元数据当成方向正确的证明。

保持原 HID、服务连接、会话 ID 与 generation，只执行一次现有录屏入口的自有媒体替换后，Apple 显示信息更新为 `rot90`，下一张截图恢复正向。该录屏请求在最终方向检查中以 `capture_context_changed` 拒绝，未开始录制。这个对照支持“替换自有媒体可促使方向更新”，尚不足以证明 Apple 内部缓存的具体实现。

两条自写只读诊断请求（直接显示服务与 CoreDevice broker）均收到 `Action ...displayinfo is not implemented`，不是权限拒绝；未继续重试，也未引入身份或 entitlement 伪装。Apple 的持续显示订阅未解决这次复现。

## 修复行为

媒体帧与显示信息的轴、尺寸或填充校验冲突时，不再退回可能使用同一旧方向的 Apple PNG。静止流中最后一帧仅可作为冲突的反证，不能成为新截图，也不能证明当前方向正确。Apple 来源的动作前保护同样运行媒体几何检查，仍保留原来源的图像比较。

每次采集最多执行一次重新同步：

1. 若正在录屏，先结束当前片段，原因记录为 `orientation_unverified`。
2. 确认 HID 就绪、媒体健康；核对 UUID 后停止本客户端媒体流，并要求确认停止。
3. 在停止之后重新读取两次锁屏与显示状态，要求显示信息一致，然后以新方向创建自有媒体流。
4. 完整重新采集、执行前后保护和图像校验。成功的观察标记 `orientationResynchronized=true`。

不重连 HID 或整个控制会话，不使用 `stopAll`，不回放输入。停止结果不确定、读取取消或重建失败会保留失败状态，不能自动重试。如果重新采集仍失败，则拒绝后续观察并要求显式重连。如果动作前保护触发了重新同步，即使新旧像素和方向字段相同，也返回 `not_dispatched`、新观察与 `stale_observation`，要求调用方重新查看和选择坐标。

状态增加 `orientationRefreshCount` 和 `lastOrientationRefreshCleanup`，用于核对恢复次数及自有流清理结果。录屏跨方向仍按既有分段契约处理，不承诺无缝连续视频。

## 修复版真机验收

解锁后首次连接因其他媒体占用返回 `native_media_busy`，未发送触控，并清理自有会话。用户结束 Device Hub 控制后重新连接成功。以下整组验收使用同一标准会话、同一 generation 和 HID 连接，始终 `runnerStarted=false`，中途没有 disconnect/reconnect。

| 操作与证据 | 实际结果 |
| --- | --- |
| 竖屏 → 左横屏 → 右横屏 | 每次方向切换后的截图均正向；元数据分别为 `rot90`、`rot270`，都标记了 `orientationResynchronized=true`。 |
| 右横屏点击右上角 B | B 从 2→3，其余角落计数不变；Probe 刷新为 UIKit 3，与 `rot270` 一致。 |
| 右横屏 → 左横屏，再点击左下角 C | 截图恢复为正向 `rot90`，C 从 2→3，其余计数不变；Probe 刷新为 UIKit 4。覆盖此前倒置的路径与独立偏心落点。 |
| 左横屏开始录制，再切右横屏 | 方向冲突结束旧录屏片段，`stopReason=orientation_unverified`；自有媒体重新同步后，新截图正向且为 `rot270`，控制继续可用。 |
| 返回竖屏 | PNG 为 1170×2532，`rot0`、UIKit 1、390×844 点一致。最终 A=3、B=3、C=3、D=2；菜单、拖拽、拖放计数仍为 0。 |

本组共 4 次方向重新同步、3 次普通显示绑定刷新、1 次显式录屏流刷新。最终均记录自有 UUID 的停止确认。期间 5 次动作前采集从媒体 PNG 切换为 Apple PNG，按既有来源保护返回 `not_dispatched` 和新观察；每次重新查看截图后才选择下一动作。没有过期观察派发，没有放宽保护阈值。实际发送的 7 次点击仍保持 `outcome=unknown`：这里的命中结论来自前后画面和 Probe 计数，而不是把队列完成当作设备确认。

录屏保存为 27.99 秒、594 帧的 HEVC MP4，全部帧解码通过。自写 AVFoundation 离线验证器再次完成解码，并抽查 1 秒与 27.9 秒：前者为正向左横屏 Probe，后者保留了旋转过渡画面。片段在检测冲突后结束，不是精确切在旋转动画前，也不证明跨方向无缝录制。沙箱内的离线解码曾返回 `Cannot Decode`；允许访问系统解码服务后，同一文件验证成功。

本次实际触发了动作后采集中的恢复。动作前恢复必须拒绝旧坐标的分支有宿主回归，但未在这组真机操作中单独触发；不得把 5 次截图来源变化拒绝算作该分支通过。真机使用 Debug 候选二进制，Release 仅验证构建。

诊断与修复版验收会话均已确认自有媒体停止、接收器/连接/隧道清理及观察缓存移除；另行检查 host 进程已退出。原始证据仅保存在忽略目录 `.local/research/native-rotation-sync-20260926/`，修复版结果汇总为 `candidate-acceptance-status.json`，截图/视频/候选二进制散列为 `candidate-evidence-manifest.json`。不提交设备标识、截图或原始协议日志。此方案检测已知媒体几何冲突，不是任意画面方向的视觉判断器；未证明可检测所有元数据陈旧情况。

## 无新鲜媒体帧时的补强（2026-09-30 至 10-01）

[新版 VRA 横屏验收](native-media-vra-repair.md)复现了另一条缺口：媒体没有新完整帧、缓存又没有显示几何冲突时，Apple 仍可能返回旧方向；返回竖屏时甚至得到横屏尺寸的侧转 PNG。之前的负面几何检查没有拒绝这类观察。

原生控制会话现在要求采集到请求屏障之后的新完整媒体帧，再检查其几何。没有帧返回 `native_snapshot_freshness_unavailable`，与已知几何冲突共用一次有界方向重新同步：确认停止本客户端 UUID 后重新读取两次锁屏/显示信息，再启动自有媒体并重新采集。普通取帧预算仍为 0.15 秒，刚刷新后的唯一重采集最多等待 1 秒；接收屏障、完整单元及 0.5 秒帧年龄检查没有放宽。旧帧和 RTCP 保活不能证明方向正确。

首版候选把所有缺帧刷新都标为 `orientationResynchronized=true`。真机已证明这会导致静止画面中的正常点击连续被拒绝：两次 B 请求都没有发送，即使用户重新查看了新图。因此最终实现区分恢复与重新确认：已知几何冲突，或刷新前后显示 ID、尺寸、scale、方向、原生方向任一改变，仍标记 `orientationResynchronized=true`；动作前必须拒绝旧引用并附新观察。仅缺帧且绑定几何完全相同则标记 `orientationRevalidated=true`，继续按原始观察检查来源、显示上下文、目标区域、全屏变化和截止时间，不跳过或放宽任何一项。`orientationResynchronizationReason` 保留触发原因。

锁屏、取消、普通图片错误不触发媒体重建；重建或唯一重采集失败则锁存 `native_orientation_unverified`，后续观察要求显式重连，不循环刷新。正常控制会话的自有媒体不可用时同样拒绝观察；启动未能建立控制的既有只读模式仍保留 Apple PNG。

静止流也可能因此多一次刷新。若正在录屏，先按现有契约结束片段并标记 `orientation_unverified`，不承诺长时间静止后观察仍能维持同一连续视频段。不改媒体协商、不改 HID 连接、不重放未知动作，也不使用 stopAll。产品截图来源目前仍是 Apple PNG；这次补强不是恢复媒体优先，也不声称能检测所有采集期间的 Apple 元数据错误。

宿主验证：首版定向 88 项（87 通过、1 项既有可选检查跳过）；最终行为的完整测试 331 项（330 通过、同一项跳过），0 失败；Release 构建成功。补充动作事实中的 `orientationRevalidated` 字段后，受影响的采集与输入测试 26 项全部通过，并重新构建最终 Release。新增回归覆盖持续缺帧不得落入 Apple 截图、最多一次同步、方向变化或已知冲突后拒绝相同像素的旧动作引用、无关错误不刷新及同步失败不继续重采集。仅缺帧且几何相同的分支分别验证原始来源、方向、像素及截止时间仍生效。既有 UUID 停止后再读显示、停止失败不启动替代流、取消与清理测试通过。

首次真机连接成功，但首次观察在停止自有媒体后重建时遇到其他媒体会话，返回 `native_orientation_unverified`，没有截图或触控。本机同时有 Device Hub 进程；没有关闭它，由用户结束对应控制会话后显式重连。自有旧 UUID 停止已确认，失败会话已正常断开并确认宿主退出。这次安全拒绝不是功能验收通过。

### 最终候选真机结果

10 月 1 日凌晨，最终 Release 候选在同一标准会话及 generation 中完成下列验证。截图始终来自 Apple PNG，`runnerStarted=false`。用户结束占用后的首次图像是其他 App，未在该 App 输入；通过 Apple CLI 打开普通 Probe 后才操作。

| 路径 | 观察与执行事实 |
| --- | --- |
| 静止左横屏点击 B | B 从 0→1。动作前缺帧刷新、几何相同，`orientationRevalidated=true`；原始画面守卫通过并在时限内发送。没有首版的重复拒绝。 |
| 左→右，点击 C，再右→左 | 依次得到 `rot270`、`rot90` 正向截图；C 从 0→1，刷新后的 Probe 文字分别为 UIKit 3、4。 |
| Right +5s 后使用旧左横屏观察 | 原观察 `o7` 为 `rot90`；动作前缺帧同步得到 `rot270`，新图标记 `orientationResynchronized=true`，返回 `not_dispatched`。C 保持 1，没有使用旧坐标发送。 |
| 查看新图后选择右横屏 A | A 从 0→1，B=1、C=1、D=0；菜单与拖放计数仍为 0。新动作正常执行，没有重放被拒绝的 C 请求。 |
| 横屏录制结束后重启 Probe | 直接得到 `rot0`、1170×2532 的正向竖屏截图，未再次输出此前的侧转图。这一次由正常显示绑定变化处理，不能算作缺帧同步分支的独立复现。 |
| 竖屏静止录制 10 秒后观察 | 缺帧触发同步；方向相同，观察标记 `orientationRevalidated=true`。自有录屏先以 `orientation_unverified` 结束，文件全量解码通过；没有偷偷延续旧片段。 |

有效发送仍为 `outcome=unknown`，上述命中结论来自图像和 Probe 计数，不来自命令退出码。B、Right、C 的动作前重新确认分别约 3.98、3.10、2.63 秒，原有 8 秒动作前预算和 30 秒观察期限未变；这是单机样本，不是延迟上限承诺。最终会话记录 9 次方向刷新、3 次显示绑定刷新及 2 次显式录制刷新，均只停止自有 UUID。

两段录制均文件校验通过：右横屏 287 帧、29.9883 秒，按 30 秒截止，约 25.22 秒静态尾部沿用末帧；竖屏静止段在约 10.59 秒观察时结束，保存 365 帧、6.12 秒。后一段因方向未验证而结束，不延长最后有效帧到停止时刻；不是包含 10.59 秒连续新画面的录像。本轮只核验文件完整解码、时长和分段事实，未对这两段新增视频逐帧目视验收，也没有触发动态小尺寸省略分支。

最终目视确认 Probe 为正向竖屏，disconnect 正常返回。自有媒体停止、隧道释放、shutdown 均确认；独立检查宿主进程不存在，socket 与观察目录已删除。私有日志与证据位于 `.local/research/orientation-freshness-20260930/`（跨日沿用目录），包括 `v2-old-reference.json`、`v2-restore.png`、`v2-static-status.json`、两段 MP4、最终二进制散列与 `v2-cleanup.json`；宿主测试和构建日志位于 `.local/research/orientation-freshness-*.log`。未发布或推送。此修复补齐本次缺帧路径；媒体截图优先仍未启用。
