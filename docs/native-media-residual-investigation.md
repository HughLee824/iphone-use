## 采集与真实动作

重新通过 Apple 发现唯一有线 iPhone 12 Pro / iOS 27.0（24A437），锁屏检查通过。Apple CLI 打开普通 iPhone-use Text Probe，读取启动完成后的 PNG 确认受控页面。标准模式全程不启动 Runner，操作前后均使用 Apple PNG。

私有诊断副本对每个媒体 generation 分开保存 RTP。每个诊断宿主的上限为 120 秒、32 MiB，实时原始解码图最多 25 张、间隔至少 5 秒。实时图保留编码画布（1184×2576），不是可用于操作的 observation。离线新旧实现收到同一批包，以实时样本的 RTP 时间戳选帧；使用合成宿主接收时间，不能作为设备捕获时间或新鲜度证明。

第一会话的输入准备消耗了采集窗口：一次长文本请求在剪贴板写入后的保护检查被拒绝，未发出 HID；确认空字段后清理事务，恢复得到确认。随后依据新截图发起一次独立替换，Apple PNG 显示 1240 UTF-8 bytes、Edits: 1，末尾为第 24 行及 `正文结束。`。但该次替换发生在 120 秒采集截止之后，**原始 RTP 没有覆盖替换瞬间**，不能声称复现了原故障的完整触发条件。

为覆盖实际变化，在长文本已准备好后补采一次约 60.72 秒的会话，仅执行一次输入框滚动，不再访问剪贴板。前后 Apple PNG 显示从第 16–24 行滚到第 11 行附近，证明滚动已发生；原生 `unknown` 回执没有被自动重放。之后结束会话，不继续循环重试。

## 追加：离线组帧、参考关系与 AVAssetReader 对照

### 独立组帧及参考关系

按 [RFC 7798 §4.4](https://www.rfc-editor.org/rfc/rfc7798.html#section-4.4) 独立处理单 NAL、AP 与 FU，在每个 marker 边界将完整 NAL 数组与产品组帧器比较。6803 包生成 4516 个 access unit、5709091 字节 NAL，**全部逐字节相等**。这个结果针对当前无 DONL、单层样本，不代表支持所有 RFC 可选模式。

所有包都带 4 字节 RTP 扩展；profile 为 `0x9001` 或 `0x9011`。扩展的前后两个 16 位值在本样本中分别与每帧包数、连续帧编号吻合：4516 组均包数相等、帧内扩展一致、编号连续。这是实测对应关系，不把它当作已经确认的 Apple 私有字段定义，也不据此修改协商能力位。

参照 [ITU-T H.265 的 SPS、slice header、短期 RPS 与 POC 规则](https://www.itu.int/rec/dologin_pub.asp?id=T-REC-H.265-201304-S!!PDF-E&lang=e&type=items)，自写有限语法读取器检查本样本的图像顺序号及短期参考集合。读到 Main profile、单层单子层、1184×2576、8-bit 4:2:0、POC LSB 11 位、DPB 上限 12、重排数 0、11 个 SPS 短期参考集合、无长期参考。图像为 1 张 I slice 加 4515 张 P slice，POC 从 0 到 4515 连续，包含两次 LSB 回绕；没有必需参考图像缺失。

这不是完整 HEVC 合规检查：读取器只处理当前样本所需语法，未验证 CABAC、运动向量、残差或全部 VUI/扩展语义。遇到未实现的关键分支会失败，不能把结果描述成“码流完全正确”。负对照在离线副本中删除 POC 3544，读取器明确报告 POC 缺口，并在 3545、3546 检出对缺失 3544 的依赖；原始数据没有这些报警。

### Apple 文件解码路径

将同一独立 NAL 前缀的 3553 帧无损封装为 MP4，使用 24 kHz 时间基准、显式 DTS/PTS 和依赖标志，交给 `AVAssetReader` 解码，绕过手写 `VTDecompressionSessionDecodeFrame` 调用。压缩读取逐个核对后，3553 个样本与封装前 AVCC 数据完全一致；解码读取也得到 3553 帧。读取器额外产生的零样本 `EmptyMedia` 标记不计入图像数量。初版诊断曾因输出目录与可执行文件重名、以及未区分该标记而失败，这两次不算验证通过。

AVAssetReader 的 POC 3545 同样损坏，导出 PNG 与直接解码的 `onset/3545.png` 文件 SHA-256 完全相同：`8633513e2062f349259e3cc36cb41c2d4160bf63a28406d723b2e5cb2e3ba004`。这进一步降低了手写解码调用中的时间基准、样本依赖标记或实时像素生命周期是唯一原因的可能性；两个路径仍共享 Apple 编解码基础设施，不能据此最终归责发送端编码器。

### 当前定位边界

本样本未发现 RTP 缺口、NAL 拼接差异或所需前序图像缺失，且在独立组帧、直接软件解码、硬件 YUV 输出及 AVAssetReader 文件解码路径上都能看到故障。剩余方向是收到的压缩图像内容、Apple 媒体协商/发送行为及共享解码实现；尚无证据支持修改产品组帧器或放宽截图保护，也没有恢复媒体观察。

### 新线索与离线对照

4516 个 VCL NAL 的末尾 14 字节有两种取值。其中 4513 帧为 `04a00a100000030000049209e403`，按前两个大端 16 位数读取是 1184、2576；**恰好 POC 3545、3546、3547 三帧**改为 `044007800000030000049209e403`，对应 1088、1920。变化从此前目视确认的首个损坏帧开始，3548 恢复原值后残影仍持续。SPS 画布仍为 1184×2576。

这提示尺寸相关元数据值得关注，但字段含义、正确处理方法及其与损坏的因果关系尚未确认，不能据此认定动态分辨率是根因。

自写两个离线变体，从独立重组的 NAL 连续解码各 3571 帧：一版只移除识别到的 14 字节尾部；另一版同时通过 Apple 的逐帧选项 API 传入 `ActiveVideoResolution`，值为读取到的 `Width`/`Height` 字典。两版均仍有残影；POC 3544、3545、3547、3548、3552 的 PNG 文件在两版之间、以及与原始未移除尾部的解码之间均逐字节相同。该私有选项的字典格式及是否实际生效未得到确认，因此不能将实验描述为“正确处理动态分辨率后仍失败”。

对自有软件解码会话查询支持属性，返回了 `ActiveVideoResolution` 和 `VideoResolutionAdaptationType`，但二者的属性描述均为空，没有提供可验证的值格式。本轮没有盲设枚举或将这些试验改入产品。

### 协商与关键帧刷新

在宿主调用与产品相同的 Apple AVConference mode 5 和网络/传输选项，生成 offer，没有启动设备服务。读取到的 codec 特征串为 `FLS;SW:1;` 和 `FLS;VRAE:0;SW:1;`；嵌套 video 消息的原始标量字段 2 为 0。历史逆向资料把该字段解释为 RTCP feedback 开关，但这不是 Apple 公布的契约，也不是当前设备接受后的 answer，不能据此直接判断设备会如何处理反馈。未改写 offer、未知能力位或 Apple 身份。

代码核对确认 `NativeMediaSession.requestKeyframe()` 构造的是 RTCP PLI（PT 206、FMT 1），不是 FIR。当前调用点位于录屏启动与重试路径。本轮没有在真机发送 PLI/FIR，也没有取得“新 IDR 到达且损坏画面恢复”的证据，不能把现有方法名或请求成功当作可靠恢复机制。

本机历史调查报告提及相似残影、FIR 产生 IDR 但仍未解决、以及 Apple 内部逐帧选项。这些仅作为线索，不算本机当前版本复测。其“普通进程无法正确解码”的结论也未由本轮证实。没有运行其中的第三方设备脚本，没有复用涉及受保护 Apple 进程调试、身份伪装或关闭系统保护的方法。

### 本轮结论与停止条件

新增证据将异常与三帧尾部疑似尺寸变化联系起来，但尚无已验证的修复或关键帧恢复方案。到此结束这轮有限调查，保留样本及诊断工具；产品继续使用 Apple PNG，不恢复媒体截图，不做推测性协议修改。

此前相同压缩数据封装的 MP4 经 AVAssetReader 也出现残影，因此 Apple PNG 观察策略只隔离了观察风险，**不能据此宣称同类媒体流的录屏画面正确**。这仍是已知限制。

后续仅在获得可确认的逐帧元数据/协商契约、有效解码配置或不同系统上的成功对照时重启调查；重复相同真机输入并不能解决当前证据缺口。

## 根因确认：Apple 动态分辨率适配未进入接收端解码链路

用户要求继续定位后，在同一故障流上完成了能改变结果的正反向实验。本轮重新核对宿主仍为 macOS 27.0（26A428）、Xcode 27.0（27A266a）；没有重新连接手机或发送输入。证据目录：`.local/research/media-root-cause-20260930/`。

### 原因与机制

本样本的编码画布为 1184×2576，但 POC 3545–3547 的有效编码尺寸降为 1088×1920，信息位于 Apple 附加的帧尾元数据中，并没有新的 SPS 更新。接收端必须在解码这些帧之前启用对应的分辨率适配，并逐帧提供有效尺寸。现有 `NativeSnapshotDecoder` 使用默认解码配置和不带 frame options 的调用，没有完成这个契约。

此前按固定画布解码时，从 3545 开始产生错误图像；尺寸在 3548 恢复后，前面的错误继续影响后续参考图像，形成持续残影。**决定性证据是：保持码流和其余解码配置相同，只将这三帧传入的尺寸改回固定画布，就重现了相同损坏。** 因此，这次已经超出“尾部变化与残影时间相关”的推测。

这确认的是当前故障样本的接收端适配缺失，不是对所有历史异常的统一归因，也不等于证明该流无需 Apple 扩展就符合通用 HEVC 播放契约。

### 有效的本机解码配置

通过只读检查本机 Apple 解码插件、读取框架导出的键值，并用自写 Swift 调用正常的 VideoToolbox API，得到以下有效组合：

| 位置 | 本机实测值 |
| --- | --- |
| decoder specification | `RequireHardwareAcceleratedVideoDecoder = true` |
| 输出像素格式 | `420YpCbCr8BiPlanarVideoRange` |
| 会话属性 | `DecoderUsage = 1` |
| 会话属性 | `VideoResolutionAdaptationType = 3` |
| 会话属性 | `NegotiationDetails = "RVRA1:0"` |
| 每帧选项 | `ActiveVideoResolution = {Width: 当前帧宽, Height: 当前帧高}` |

所有属性设置和每帧解码状态均核对；`UsingHardwareAcceleratedVideoDecoder` 实际读取为 true。`RVRA1:0` 是本地解码会话的参数，没有发送给手机，也没有改写媒体 offer。上述私有属性值是本机实验证实的配置，不把枚举含义或跨版本稳定性当作 Apple 公开保证。

框架导出的 `kVTDecompressionPropertyKey_Usage` 实际字符串为 `DecoderUsage`。诊断过程中曾用错 `Usage`，得到 `-12900`；这两次立即失败，不算有效解码实验。不存在的 DecoderID 负对照返回 `-12906`，说明显式解码器选择确实受系统校验。

### 正反向结果

完整正例 `full-original-nals` 原样保留所有 NAL 字节，包括尾部，从起始 IDR 连续解码 **4516 帧**，没有请求新 IDR、修改压缩内容或跳过故障帧。保存的 12 张图覆盖 POC 0、3544–3548、3552、3560、3570、3600、4000、4515。目视检查原始损坏边界、替换后正文及末帧：文字碎块和旧末尾残留消失，最后一帧显示本轮新正文与新末尾。不能把解码成功数量等同于逐帧人工检查。

最终保存的 `decode-v8` 再次完整解码 4516 帧，12 张抽样 PNG 与首次完整正例全部逐字节相同，硬件状态再次确认；结果保存在 `verified-v8/` 和 `final-verification.json`，证据哈希见 `evidence-sha256.json`。

| 对照 | 解码帧数 | 结果 |
| --- | ---: | --- |
| 完整有效配置，保留原始 NAL | 4516 | 故障边界及后续抽样图清晰，末帧清晰 |
| 相同配置，仅三帧尺寸固定为 1184×2576 | 4516 | 从 3545 再现残影，持续至末帧 |
| 移除 `NegotiationDetails` | 4516 | 12 张抽样 PNG 与固定尺寸负例逐字节相同 |
| 移除 `VideoResolutionAdaptationType` | 4516 | 12 张抽样 PNG 与固定尺寸负例逐字节相同 |
| 移除 `DecoderUsage`，其余配置保留 | 3571 | 已查看的替换后图仍损坏 |
| 完全不传逐帧尺寸，其余配置保留 | 未完成 | 首帧无可用图像，返回 `-12909`，不是通过 |

最直接的固定尺寸负例只改变 POC 3545–3547 的解码选项，不改变输入字节。正负例在 POC 0、3544 的 PNG 完全相同；从 3545 起，保存的 10 张负例 PNG 均与故障对照逐字节相同，且与正确配置不同。这支持“尺寸适配缺失导致参考链持续失真”的解释，而不是显示层遮盖、PNG 修补或恰巧拿到新的清晰画面。

移除尾部的早期成功实验与保留尾部的正例，9 张共同抽样图逐字节相同。因此，“只剥离尾部”不是修复关键。此前硬件/软件、AVAssetReader 等对照都没有建立完整适配条件，不能用它们排除 Apple 解码配置，也不能再沿用历史资料中“普通进程无法解码”的结论。本次成功发生在自写普通宿主进程中，没有系统进程注入、身份伪装或关闭系统保护。

### 产品修复范围与尚未验证项

根因及离线有效方案已确认，**产品代码尚未改动，媒体截图隔离仍保留**。接入时至少需要处理以下实际问题：

- 将经过校验的逐帧尺寸元数据送入解码链路，并明确选择已验证的解码配置；遇到未知格式或不支持的配置时返回失败，不能静默当作普通 HEVC 继续使用。
- 修正有效画面与观察坐标之间的几何处理。正例的 3545 原始像素缓冲中，有效图像确实缩小，画布其余部分为灰色；清晰的原始解码图还不等于已完成归一化的 observation，不能放宽现有填充区保护直接启用。
- 录屏不能只把带这种适配行为的原始 HEVC 封装成 MP4 就宣称通用可播放。此前 AVAssetReader 残影由此得到解释；修复需验证经正确解码、几何归一化后重新编码的常规视频，或另行验证等效且可移植的存储方案。
