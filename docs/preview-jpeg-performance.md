# JPEG 与动态分辨率预览验证（2026-10-18，未发布）

## 改动与边界

预览改为使用 `CIContext.jpegRepresentation` 直接导出 JPEG，省去显式 `createCGImage(..., deferred: false)` 和独立 ImageIO destination。沿用两槽有界并发、旧结果丢弃、CPU Core Image 上下文、原生像素裁剪、方向校验、边缘延展、最长边 960、JPEG 质量 0.7 和色彩管理。没有提高 30 fps 上限，也没有减少分辨率、绕过方向守卫或改变录屏/控制通道。

Core Image 内部完成渲染及压缩，API 不暴露阶段分界。因此 `lastEncodeMs` / `maxEncodeMs` 继续表示合计墙钟耗时，`timing.stageTiming=combined`；原来的转换/压缩最大值字段为 `null`，不是零。JPEG 字节不保证与旧编码器完全相同。

## 方法

- 主机：Apple M1，8 核，16 GiB RAM；测试中读取到内存压力级别 2，swap 已用约 920 MiB。未关闭用户应用，也未人为制造内存压力。
- 设备：USB iPhone 12 Pro / iOS 27.0.1，standard 模式，每组对比在同一个 Chrome 测试页中切换版本。未录屏。浏览器窗口状态不是严格受控实验变量，前端指标只作为本机观察结果。
- 场景：已有 NativeTextProbe 的 `--preview-scroll-probe`。UIKit 表格包含文字和图标，以相同八秒曲线往返滚动。程序设置真实表格的 contentOffset；它用于可重复的渲染负载，不是人工手势或触摸到屏幕的端到端延迟测试。
- 测量期间不编译、不运行单元测试或其他编码实验；前后版本顺序运行并正常断开。基线二进制在源码修改前构建并保留。
- `scripts/preview-soak.py` 每秒采样宿主状态、CPU、RSS 和 JPEG 大小；浏览器使用 `?diagnostics=1` 的图片加载 + rAF 数据。按宿主采样起止时间截取窗口，排除窗口外的启动、结束事件。
- 浏览器导出使用已有的最近 1,800 帧缓冲区。第一段基线导出存在时间缺口，浏览器分位数仅描述实际保存的样本；累计慢帧事件在本次窗口内未达到 120 条上限。不能把缺口当作无卡顿。
- 原始数据、测试视频/截图、候选实验和二进制 SHA-256 保存在忽略目录 `.local/preview-perf-20261018/`。不随项目分发设备画面或会话 URL。

## 真机滚动结果

以每秒状态采样中的 `lastEncodeMs` 比较 JPEG 合计耗时。CPU 为 `ps %cpu` 的宿主进程值（100% 约为一个逻辑核），不包含浏览器、系统服务或设备端工作。

| 窗口 | 时长 | JPEG 中位数 ms | JPEG P95 ms | 宿主 CPU 中位数 | 浏览器 >100 ms / >250 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 基线 A | 180 秒 | 6.45 | 12.20 | 24.4% | 1 / 0 |
| 候选 B | 180 秒 | 4.13 | 5.86 | 20.7% | 0 / 0 |
| 基线复测 A | 120 秒 | 9.00 | 12.31 | 25.9% | 1 / 0 |
| 最终构建复测 B | 120 秒 | 4.25 | 6.02 | 21.7% | 0 / 0 |

两组有效对比合计十分钟，四个窗口各自连续采样成功，无解码错误或解码队列溢出。首组 JPEG 中位数减少约 36%，P95 减少约 52%，宿主 CPU 相对减少约 15%；最终构建复测的对应改善约为 53%、51% 和 16%。JPEG 平均大小从约 79.5 KB 到 80.6 KB，增加约 1.4%；不是通过降低清晰度或减少输出尺寸取得收益。

首组浏览器已保存样本的帧间隔 P95 均约 49 ms，P99 为 50 / 51 ms；复测 P95 为 34 / 35 ms，P99 为 35 / 50 ms，并没有同步改善。有效窗口中观察到的最大间隔分别为 101 / 84 ms、116 / 68 ms，但事件数不足以建立稳定性保证。**编码开销下降已有证据，但不能据此宣称偶发卡顿已经根治。** 超过 100 ms 的事件数量很少，两个有效首组窗口都没有复现历史上的数百毫秒长尾；更换应用、浏览器、系统负载或录屏时仍需复测。浏览器指标是 `image.onload + rAF` 绘制机会，不是物理屏幕呈现或手机到电脑的端到端延迟。

一次中间复测发现手机已回到主屏，连续滚动场景中断；该轮静态画面的秒级新帧间隔全部排除，原始数据以 `baseline-repeat-exclusion.json` 记录原因。重新启动测试应用后才进行有效基线复测，未把静态不出帧误判为性能故障。

## 用户真实应用反馈后的补充排查（修复前）

用户确认自动往返列表没有明显卡顿，但真实应用操作存在明显卡顿。重新检查四个有效采样窗口，`framesWithoutImage` 的起止值分别为 `0→0`、`0→0`、`0→0`、`63→63`，窗口内增量全部为零。最后一组启动前已有的 63 次不能算进测试窗口。

随后手动体验会话的一次状态快照中，`decodedFrames=6326`、`framesWithoutImage=1986`，同时 `decodeErrors=0`、`queueOverflows=0`、`referenceResets=0`。这是会话累计值，不能当作用户录屏区间的丢帧率，也没有与具体手势时间对齐。证据保存在 `.local/preview-perf-20261018/user-recording/current-state.json`。

当前 `NativeSnapshotDecoder` 对非完整分辨率画面仍解码以维护参考链，但返回 `nil`；`NativeVideoSnapshot` 对这类视频单元增加 `framesWithoutImage` 并清除可用帧，预览则继续保留前一个 JPEG。这是此前 VRA 修复保留的已知呈现限制，见 [尺寸与失败策略](native-media-vra-repair.md#尺寸与失败策略)。`framesWithoutImage` 本身不是专用的低分辨率计数，不能仅凭累计值认定全部事件的原因；但它揭示了原自动滚动测试完全没有覆盖的可用画面中断路径。

后续验收需要覆盖停顿后操作、点击进入/返回和惯性滑动，将源帧有效尺寸、是否输出画面以及浏览器更新时刻对齐。当前证据只支持把动态分辨率呈现列为优先排查方向，尚未证明它解释录屏中的每次卡顿。JPEG 开销下降不能替代这一验收。

## 动态分辨率修复与真实 App 验收

上述排查已继续完成。确认的缺陷是：动态小尺寸帧虽然正确参与 HEVC 参考链解码，却被呈现层省略。连续收到这些帧时，浏览器只能保持上一张完整尺寸画面。JPEG 编码耗时下降不能修复这个缺口。

### 实现

- `NativeDecodedVideoFrame` 携带经过既有元数据校验的 active 宽高。共享解码器为浏览器保留 reduced 帧；现有 full-resolution 缓存、截图新鲜度、录屏预备帧和录屏订阅仍只接纳完整尺寸画面。
- 预览按 `nativeWidth × activeWidth / canvasWidth` 和 `nativeHeight × activeHeight / canvasHeight` 取得左上方有效内容，去掉同比缩小的右/下填充，恢复原生坐标轴后再旋转和缩到最长边 960。不能直接把整个 active 矩形拉满屏幕，否则把编码填充也拉进来。
- 方向检查仍执行；异常尺寸、未知元数据和解码错误仍拒绝。方向探测也可使用 reduced 帧的已有方向标记与规范化预览。
- 状态新增 `previewDecodedFrames`、`reducedResolutionFrames` 与最多 120 条 `resolutionChanges`；`decodedFrames` 继续表示完整尺寸帧。HTTP JPEG 响应新增实际所用源帧的 active 宽高，便于核对动态帧是否真的送达，不能将“解码了”当成“显示了”。

### 几何和同一故障流回放

对既有 Apple VRA 故障流连续回放 4,516 帧，原先省略的 3545–3547 三帧现在均可生成预览，未省略任何画面。检查三种旋转下的抽样 JPEG，未见灰色填充区或恢复完整分辨率后的持续残影。该回放是旧故障流证据，不能冒充本次小红书的相同压缩输入。

几何负对照：将三张 1088×1920 active 矩形直接拉伸，与前一完整帧的固定底部工具栏比较，RGB 平均绝对差约 20.14/255；按画布比例裁剪后约 1.34/255。该数字只衡量固定工具栏区域，不把正在变化的编辑内容当作一致性证据。

### 本机真实 App 对比

同一 USB iPhone、同一 Mac、同一 Chrome 标签页，使用小红书中用户录屏里的摄影卡片。实际完成点击进入详情、上滑正文、返回信息流，每步均检查新的 Apple PNG 确认页面。未录屏、未使用自动滚动夹具，测量期间未编译或运行测试。

旧构建在进入详情时省略 7 帧、返回时省略 10 帧；相应 100 ms 状态采样里预览计数不增长，旧画面年龄升至约 411 / 461 ms。加上打开应用阶段，共 9 个“未输出画面计数增加”的采样间隔，9 个间隔的 JPEG 计数全部不增长。上滑正文这一轮没有触发动态小尺寸分支，因此不能宣称每一次滑动卡顿都由此导致。

新构建在相同点击/返回过程中实际送出了 1088×1920 来源的 JPEG，抽样画面比例、工具栏、边缘正常。CLI 操作后的自动校验截图仍可触发独立的媒体重建；这两段进入/返回操作合计出现 44 次 HTTP 503 采样。因此**不将 CLI 操作的整段等待或媒体重建混算成纯手动预览性能，也不宣称该副作用已修复**。省略 `--observe` 的尝试仍因未知 HID 结果自动附带截图，不能视为无截图干扰实验。

旧构建采样脚本中 `ps` 受沙箱限制，所有行被脚本记为失败；但 1,733 行状态均已保存，1,667 行 JPEG 哈希已保存。这里只使用已取得的状态时序，不使用不存在的 CPU 结果，也不把 66 次 JPEG 失败当成无卡顿。计数跨媒体重建会归零，对事件按相邻采样的正增量核对，不能直接用整个窗口末值减初值。

## 架构选择

当前链路为：手机 HEVC → Mac 解码 → JPEG 导出 → HTTP → 浏览器 JPEG 解码。连续滑动时，相邻帧大量内容相似，但 JPEG 每帧仍独立编码；每帧新建 HTTP 连接、Blob 和图片加载也存在固定开销。这次减少了中间图像构造，仍保留这些结构性成本。

| 方案 | 可减少的成本 | 主要约束 |
| --- | --- | --- |
| 直接 JPEG（本次） | 显式 RGBA CGImage 及独立导出步骤 | 每帧独立压缩、浏览器独立解码仍在 |
| JPEG 持续连接/推送 | TCP 建连、逐帧请求周转 | 不解决 JPEG 转换和压缩；必须限制慢客户端积压 |
| 硬件 H.264 + WebCodecs | 用帧间压缩替代独立 JPEG，浏览器用视频解码器 | 仍需 Mac 转码；要实现硬件能力探测、关键帧恢复、旋转重配、有界队列、浏览器回退；需要另做真机 A/B |
| 原生 Mac 窗口直接显示 CVPixelBuffer | 省去 JPEG/H.264 再编码、HTTP 和浏览器再次解码 | 新增原生 UI 和窗口生命周期，失去纯浏览器预览的便利 |
| 直接将手机 HEVC 转发浏览器 | 理论上省去 Mac 重编码 | 现有流依赖 Apple VRA 解码配置（RVRA1:0）及完整分辨率判断，不能假定普通浏览器 HEVC 解码正确；当前不可作为已验证方案 |

若目标是继续支持浏览器并进一步降低 CPU/带宽，下一步值得做独立的 **硬件 H.264 + WebCodecs 原型**，先比较编码时延与浏览器队列，而不是直接替换现有入口。队列必须有界；不能在依赖链中任意丢压缩帧，积压时需要关键帧恢复。若目标是单纯获得本机最高效的画面显示，原生像素显示路径更直接。这些是架构分析，不是本轮已完成的性能验证。

依据：[Apple Core Image JPEG 导出](https://developer.apple.com/documentation/coreimage/cicontext/jpegrepresentation(of:colorspace:options:))、[Apple 低延迟视频编码](https://developer.apple.com/documentation/videotoolbox/encoding-video-for-low-latency-conferencing)、[W3C WebCodecs](https://www.w3.org/TR/webcodecs/)。

## 2026-10-19 自主真实 App 验收

结论：动态分辨率呈现修复通过本轮覆盖；实时预览整体性能仍有待修问题，不能标为完全无卡顿。未修改生产代码，使用上节相同修复版 release 二进制（SHA256 `d2ba76605f055e0c987e8e9d24bed592f4eb24db51ca6975e7aebed3c8e55fcd`）。

### 覆盖与方法

同一 Mac、USB iPhone 12 Pro、原 Chrome 预览标签页。旧会话已丢失设备连接，先关闭旧本机资源，再以原 standard 模式建立新会话。旧会话的 backend/receiver 已关闭，但因连接已断，设备媒体停止确认未收到；新会话最终健康。全程未录屏、未编译、未使用自动滚动夹具。

完成 16 次实际导航/滑动操作，每次检查附带的新 Apple PNG：小红书摄影文章慢速上滑、快速上滑、反向滑动、返回信息流、进入另一篇摄影图文、横向切换图集、返回及信息流滚动；设置应用返回 General 和快速滚动；Safari 原有网页滚动；切回小红书，并停留约 50.5 秒后再次滚动。Safari 两次安全校验拒绝均未派发输入；查看新画面后把手势路径移到动画上方，第三次成功完成滚动。没有修改手机设置或提交社交内容。

## 2026-10-19 浏览器图片等待排查与预解码改进

本轮针对上一节的 277 / 332 ms 间隔。旧 `imageLoadMs` 从取得 Blob 后计时，直到 `onload` 后执行 `layout()` 才结束，混合了 Blob URL 图片请求、事件调度和布局，不能直接等同 JPEG 解码 CPU 耗时。旧页面没有长任务记录，无法事后确认两次长等待的具体原因。

### 实现与边界

`NativePreviewPage.swift` 改为在离屏 `img` 上调用 `decode()`，成功后替换当前显示图像。只保留一张当前图和一张候选图，不增加请求队列；失败时释放候选 Blob URL，保留上一张有效图像并沿用原重试策略。成功后释放旧 URL。等待期间发生的 resize / 健康状态样式变化会在替换前重新复制，避免旧样式覆盖新布局。尺寸、旋转均不变时跳过每帧 `layout()`；resize、设备资料更新、旋转和尺寸改变仍走原布局逻辑，手势覆盖层保持独立。

新增 `bodyMs`、`decodeWaitMs`、`layoutMs`，诊断模式用最多 120 项的 Long Tasks 记录辅助定位主线程阻塞。`decodeWaitMs` 仍是包含调度的墙钟时间；不支持 Long Tasks 的浏览器不采集该项。旧版 onload 与新版 decode 完成不是同一测量终点，不能直接比较这两个耗时百分比。指标仍是 rAF 绘制机会，不代表屏幕物理呈现时间。

设计依据：[HTML 标准的 decode() 合约](https://html.spec.whatwg.org/multipage/embedded-content.html#dom-img-decode)允许在解码完成后将图片插入 DOM，并要求尽可能将解码结果保持到下一次渲染更新。该合约支持减少同步显示路径上的工作，**不保证消除系统调度、内存压力或上游供帧抖动**。
